# common-dev-log

作業の **あと** に使うSkill。記憶が新しいうちに、Obsidian用のログを作る（**Obsidianが正本**）。**ユーザーが指示しなくても、下記の発動タイミングに該当すればClaude Code本体が自動的に使う**（詳細判断基準は[[AI-Workflow-System/01_harness/作業ログ自動運用_正本]]）。

**2026-07-22改訂**：Notion用ログの自動生成は廃止した。以前はObsidian用とNotion用を常にセットで作る設計だったが、現在Notionはほぼ使用されておらず、AI生成ログをNotionへ転記する運用も終了している。Notion用ログは、ユーザーが明示的に依頼した場合のみ追加で作成する。

## 発動タイミング（自動）

まとまったタスク完了・重要成果物作成・重要仕様判断確定・commit・外部設定変更・実機確認完了・エラー原因と解決の確定・作業テーマ切替・セッション/チャット移動・作業中断・次回再開地点確定・ユーザーが「今日はここまで」と言った時。軽微な確認・試行錯誤・途中経過は逐一記録しない。

**呼び出し設計（2026-07-17追記）**：本Skillのdescriptionだけに自動発火を委ねない。commitを伴う作業では、[[AI-Workflow-System/01_harness/最小ハーネス運用_正本]]§19のcommit前ゲートでログ要否を先に判定し、必要と判定した場合だけ本Skillを呼ぶ。全作業で無条件に読み込む設計にはしない。

## セッション終了条件との関係（2026-09-12追記）

本Skillは**実装補助**であり、存在するだけでは発動しない。ログを残す責任はSkillではなくClaude Code本体の**セッション終了条件**にある（[[AI-Workflow-System/01_harness/作業ログ自動運用_正本]]§18-3）。セッションを終える前・Human確認待ちで止める前に、本体が次を確認してから本Skillを呼ぶ。

1. 作業ログ対象か（**監査・レビュー・設計判断だけのセッションも対象**。変更ファイル0件は不要の理由にならない）
2. 同日・同テーマの既存ログを検索し、新規／追記を決める
3. 作業内容・現在地・次アクション・**Human-required**（Humanが何をすれば次へ進むか）を書く
4. commit・push結果（hash・停止理由）を書く
5. Hub反映判定を1行残す
6. 完了報告に「作業ログ：作成／追記／不要（理由）」を1行書く

**「no Vault」「正本を変更しない」「正本変更禁止」は、開発ログの作成・追記を禁止しない**（同正本§18-4）。正本・企画・設計書・台帳を書き換えないという意味であり、`02_Development-Logs/`への記録は別概念。作業ログまで不要にする場合はHumanが「作業ログ不要」と別途明示する。Vaultを作業ディレクトリに持たないセッションでは、repo側に置き場を作らず「Vault側ログ未作成」を完了報告へ明記し、次にVaultを開くセッションで補完する。

## このSkillがやること

- その日の作業を構造化してログにする
- 次回AIに渡す引き継ぎプロンプトを作る
- Obsidian用（リンク重視）を用意する（標準はこれのみ。正本はObsidian）
- ユーザーが明示的に依頼した場合のみ、Notion用（貼り付け用）を追加で用意する
- 既存の同日・同テーマログを検索し、新規作成/追記を判断する

## このSkillがやらないこと

- コードの変更
- 既存ログの上書き（追記条件を満たさない場合は新規ファイルとして作る）
- 複数Agentによる同時書き込み（正式ログへの書き込みは本体のみ）

## 新規作成 / 追記の判断

1日1ファイルへ全作業をまとめない。**プロジェクト／作業テーマが同じ日は追記、違えば同日でも新規作成**する。迷ったら「後からプロジェクト名・テーマ名で追えるか」を優先する（詳細基準：[[AI-Workflow-System/01_harness/作業ログ自動運用_正本]]2節）。同じ親タスクの子工程（Phase 1／Phase 2、MA-01／MA-02のようなID）を別ファイルにする場合も、担当AIが変わっただけで分断しない・実行タスク台帳への登録と親ログとの相互リンクを必須にする・frontmatter欠落のログを作らない（2-4節）。

## 命名規則

- 開発ログ：`YYYY-MM-DD_プロジェクト名_開発ログ.md`（プロジェクト名部分はテーマまで具体化してよい）
- Notion用（明示依頼時のみ）：`YYYY-MM-DD_プロジェクト名_Notion用.md`
- 再開メモ：`YYYY-MM-DD_プロジェクト名_再開メモ.md`

## 開発ログ（詳細版）フォーマット

```md
# YYYY-MM-DD プロジェクト名 開発ログ

## 今日やったこと
## 発生した問題
## 原因・仮説
## 実施した修正
## 現在の状態
## 次回やること
## 次回AIに渡す指示
## Git保全確認
## 技術スタック変更判定
## 自己進化ループ判定
## Hub反映判定
## 関連ファイル・関連メモ
```

「Git保全確認」は`git-hygiene` Skillの出力フォーマットで埋める（項目定義の重複記載はしない。詳細は`.claude/skills/git-hygiene/SKILL.md`参照）。重要資産を変更した作業では、この節を空欄のまま完了扱いにしない。

「技術スタック変更判定」（2026-08-19新設・MA-19）は**作業差分から軽く判定**し、次の4項目を1〜4行で書く。判定のために台帳を読み込まない。変更がなければ「技術スタック変更：なし」の1行で終わってよい。

```
- 技術スタック変更：あり／なし
- 台帳更新：必要（対象台帳名）／不要
- PC共通設定への影響：あり／なし
- 他PCへの反映必要：あり／なし
```

判定基準（「あり」の例・「なし」でよい例・更新先）は[[AI-Workflow-System/01_harness/技術スタック選定・管理_正本]]§5を正本とし、ここに重複記載しない。commit前ゲートとの関係は[[AI-Workflow-System/01_harness/最小ハーネス運用_正本]]§19-5参照。

「自己進化ループ判定」（2026-08-26新設・MA-21）は、その作業が自己進化ループPhase 1の対象かを**1行で判定**する。**S規模・文言修正・設定値のみ・単純調査・文書や台帳のみの更新は対象外**であり、その場合は「自己進化ループ：対象外（S規模）」等の1行で終わってよい。判定のために正本を読み込まない。

対象になるのは、**M／L規模の実装作業が完了した場合のみ**（サイズ判定は`.claude/skills/context-diet/SKILL.md`「サイズ判定」が正本）。**Phase 1は1件だけ**実施し、2件目以降は人間の継続判断が出るまで実施しない（その場合も判定は行い「Phase 1実施済み・継続判断待ち」と1行書く）。

```
- 自己進化ループ：対象／対象外（理由を1行）
```

対象と判定した場合に限り、次を追記する（**新しい台帳・スコアリング表は作らない**）。

```
- 実コスト概算：
- 再作業・問題：あり（内容1行）／なし
- 還流候補：あり／なし
- 還流先：Brain／正本／Skill／なし
```

中核指標3項目（`rework_count`／`human_interventions`／`repeat_miss`）は本文ではなく**frontmatter**へ入れる（[[AI-Workflow-System/01_harness/AI開発知識資産・自己進化ループ設計]]§14）。対象判定条件・対象外条件・記録項目・Human approval範囲の正本は同設計§17であり、ここに重複記載しない。commit前ゲートとの関係は[[AI-Workflow-System/01_harness/最小ハーネス運用_正本]]§19-6参照。

「Hub反映判定」（2026-09-05新設・MA-25 §60-3）は、その作業でEN Product Hubの**現在地が変わったか**を1行で判定する。変わっていれば既存の`hub sync-add`で送信箱へ積み、何を積んだかを書く。**ユーザーが「Product Hubにも反映して」と言わなくても、この判定は毎回行う。** 判定のために台帳・Hubのデータを読み込まない。

```
- Hub反映：あり（積んだイベント種別と件数）／なし（理由1行）
```

積む例（Project statusの変更・現在地／次にやる1件の更新・task／milestoneの追加や状態変更・ideaの登録や状態変更・Project Type初回登録・事業イベント）と、積まない例（文言修正・誤字・内部リファクタ・Hubの現在地に影響しない変更・未確定のもの）の正本は[[AI-Workflow-System/07_project-kits/AI開発環境改善マスタープラン_EN-Product-Hub構想_2026-08-30]]§60-3-3であり、ここに重複記載しない。commit前ゲートとの関係は[[AI-Workflow-System/01_harness/最小ハーネス運用_正本]]§19-7参照。

**Claude Codeが行うのは送信箱へ積むところまで。** `sync-push`・Hubの更新ボタンはHuman-only。報告には「Hubへ反映しました」ではなく**「Hubに更新が◯件届いています。更新ボタンを押してください」**と書く。Humanの反映操作は`hub-update`の1コマンド（同正本§60-4）。

## Notion用フォーマット（ユーザーが明示的に依頼した場合のみ使用。標準では生成しない）

```md
# YYYY-MM-DD 作業ログ

## 概要
## 作業内容
## 決定事項
## 問題点
## 次回作業
## 引き継ぎプロンプト
```

## 手順

1. 同日・同テーマの既存ログがないか検索する（材料収集はAgent委任可。[[AI-Workflow-System/01_harness/Agent_SubAgent委任ルール]]第3-1節）
2. 今日の作業内容を聞き取り、または差分・履歴から要約する
3. 問題・原因・修正・現状を分けて整理する
4. 次回やること、引き継ぎプロンプトを作る
5. 追記条件を満たせば既存ファイルへ追記、満たさなければ新規ファイルを生成する（日付は今日の日付）
6. Obsidian用のみを作成する。ユーザーがNotion用を明示的に依頼した場合のみ、Obsidian用とは別に追加作成し、内容を混同しない
